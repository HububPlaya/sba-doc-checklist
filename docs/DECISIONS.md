# Decisions

A running log of the deliberate scope and architecture calls made on this project, and why. Written so any of these can be explained on demand — not just executed silently.

| Area | Decision | Why | Alternative considered |
|---|---|---|---|
| **Architecture** | Next.js (App Router), single codebase for frontend + API routes | One process, one `npm run dev`, fits the "run locally in under 5 minutes" requirement | Separate React + Express repos — rejected for extra folder/process overhead with no real benefit at this scale |
| **Database** | SQLite via `better-sqlite3`, no ORM | Zero-config, synchronous, file-based — fits a standalone, no-existing-systems tool; raw SQL is faster to write correctly than fighting an ORM for ~5 simple queries | Prisma — rejected for schema/migrate/generate overhead not justified at this size |
| **Auth** | Auth.js (NextAuth) with a Credentials provider, seeded from known users | Real provider/session/middleware architecture — swapping in company SSO later is a config change, not a rewrite. No external account or network dependency needed to run locally | Clerk/Auth0 (legitimate for production, rejected here for external account + network dependency in a local-only build); roll-your-own auth (rejected — reinvents a well-known pattern under time pressure); cookie-based name picker (rejected — doesn't represent real auth architecture) |
| **Session length** | 8-hour JWT session | Correlates to a workday — Auth.js's 30-day default and a 1-hour session were both rejected as not matching real usage (30 days is excessive for a work tool; 1 hour forces disruptive re-logins mid-task) | 30-day default; 1-hour session |
| **Application status** | Computed on read (Complete/Outstanding/Stalled), not stored | Avoids two sources of truth — a stored status field can drift from the underlying document statuses the moment one updates | Storing application-level status as its own column |
| **"Stalled" definition** | At least one document not `Approved`, and no update in `STALLED_THRESHOLD_DAYS` (5 business days) | Turns the team's #1 named pain point ("not knowing which applications are stalled") into an explicit, explainable rule instead of a vague label | — |
| **Status transitions** | Backwards transitions allowed (e.g. Approved → Pending) | Matches real loan processing — documents get kicked back; also correctly resets the stalled timer | Forward-only transitions |
| **CSV import policy** | Upsert on `(application_id, document_type)`, normalized match | Supports the realistic ongoing need — re-importing fresher exports over time — without wiping existing work | Full replace (rejected — destroys in-app edits on re-import); insert-only (considered first, upgraded to upsert once ongoing re-imports became the expected pattern) |
| **Import field protection** | `status`, `notes`, `updated_by`, `updated_at` are protected from overwrite on re-import; `loan_amount`, `application_date`, `business_name` are overwritable | Protects human-entered work in the tool while still letting source-of-truth fields (loan amount, etc.) refresh from a new export | Upsert with no field distinction — rejected, risks silently overwriting a processor's status update |
| **Unknown document types on import** | Imported and flagged, not rejected | Avoids silently losing real data over a naming mismatch | Rejecting unrecognized types |
| **Malformed rows on import** | Skipped individually, reported by row number; import continues | One bad row shouldn't fail the whole batch for a non-technical user | Aborting the entire import on any bad row |
| **Missing-document-type detection** | Cut — tool only tracks documents it has records for | Unconfirmed whether the team currently tracks against a fixed 12-type checklist; building strict detection would invent a requirement rather than serve a confirmed one | Diffing a master 12-type list against what's present per application — logged in `FUTURE.md` as a fast follow |
| **Delete** | Soft delete only (`archived_at`), no hard delete | SBA document trails likely carry real retention expectations; audit trail (`updated_by`/`updated_at`) elsewhere in the app would be undermined by allowing destructive deletes | Hard delete with cascade + confirmation — considered, rejected for consistency with the audit-trail decisions made everywhere else |
| **Roles** | Two roles (`processor`, `team_lead`), one gated action: archive | Narrow, single-purpose role check rather than a general permissions system — nothing else in the brief calls for different capabilities per role | Broader per-role view differences — not built, not requested |
| **File storage (uploaded CSVs)** | Not persisted — parsed in-memory, discarded after import | No requirement to keep the raw file; import summary is a sufficient record for a 3-person internal tool | Local filesystem storage; SQLite blob storage — both easy to add later, logged in `FUTURE.md` |
| **Notifications** | Both: an always-on in-app banner, and real email alerts via Resend | The brief asked for email specifically. The in-app banner covers the moment the team is already in the tool (they log in daily), and real Resend email — on the shared test domain, zero DNS setup — closes the literal brief requirement on top of that, since Resend's setup cost turned out to be low (~30 minutes) once the in-app version was already built | Email-only (the literal brief ask, considered first); in-app-only (the initial plan, before Resend's low setup cost changed the calculus) |
| **Email alert trigger** | Runs on dashboard page load, not a scheduled job | No real scheduler available for a local, non-deployed tool — this is the honest local-tool stand-in for a cron job | A manual "Send Alert Now" button (considered, rejected in favor of automatic) |
| **Email alert dedup** | `alert_sent_at` timestamp per document; only un-alerted expiring documents are sent | Prevents the same alert firing every time anyone opens the dashboard, which would train the team to ignore it | No dedup — rejected, would produce alert spam |
| **CSV/import summary copy** | One plain-language sentence, no status codes or technical terms | This is the one screen where a non-technical user is most likely to feel something went wrong if the message reads as technical | Verbose/technical error detail |
| **Empty states** | Show guidance on what to do next, not a blank table | A blank table reads as broken to a non-technical user; explicit guidance reads as intentional | Blank/undecorated empty table |
| **First-boot state** | Empty database, Import screen is the landing page — no auto-seed | Matches how the team would really onboard (their first action is importing their spreadsheet); doubles as the first beat of the demo | Auto-seeding from the sample CSV on first boot |
| **Concurrency** | Last-write-wins per document row, no conflict-resolution UI | Each document row is independently owned, so real collisions are rare; building conflict resolution isn't justified for a 3-person internal tool | Optimistic UI with rollback/merge logic |
| **Undo** | None beyond the existing `updated_by`/`updated_at` audit trail | A wrong status click is just clicked back; the audit trail already answers "who changed what, when" without separate undo logic | A dedicated undo/audit history feature |
| **Loan amount display** | Formatted as currency (`$390,000`), not raw integer | Small detail, but "looks like the spreadsheet they know" credibility matters for a non-technical audience | Displaying the raw stored integer |
| **Testing scope** | Full unit coverage on the domain layer, targeted integration tests (archive role-gate, alert dedup), one E2E critical path | Concentrates effort on the highest-risk logic (upsert correctness, the one real security boundary) given the time box; broader coverage is a described QA plan, not code, per the brief's own guidance that this is acceptable | Broad test coverage across every layer — not justified against the 3–4 hour time budget |
